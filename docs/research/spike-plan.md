# NOESIS: engine spike plan (draft 0.1)

Companion to [engine-choice.md](../architecture/engine-choice.md). The recommendation there (Pyodide in one Web Worker, same Python node code in an optional native companion) rests on several facts nobody has measured yet. This plan defines a short, throwaway experiment that confirms or kills each of them **before** any product code is written.

**Status:** run 1 is done on the Mac in one Chromium browser. Results and verdict (go, with adjustments) are in [spike-results.md](spike-results.md). Windows, NVIDIA GPU, Firefox and Safari are still to run.

All numeric thresholds below are **proposals**. Agree or change them before starting, so nobody moves the goalposts after seeing results.

## Goal

Answer one question with evidence: *can Pyodide run the v1 tabular workflow well enough on a typical professional's laptop, with live training events and working cancellation, and can the same node code run natively?*

Output: a go / adjust / no-go decision recorded in [spike-results.md](spike-results.md), plus concrete limits to build into the product (file-size cap, preset sizes, default engine per workload).

## Scope and non-goals

In scope: the engine only (loading data, profiling, training, events, cancel, caching, browsers).

Out of scope: any wizard UI, the rule engine, polished visuals, deep learning, authentication, the companion's security design.

All spike code is throwaway. It lives in the `experiments/engine-spike/` folder and is not reused unless it happens to be good.

## Setup

| Item | Detail |
|---|---|
| Pyodide | Latest stable release at start. Record the exact version and its package versions. Self-hosted (not from a CDN). |
| Server | A tiny static server that sets the cross-origin isolation headers (`Cross-Origin-Opener-Policy`, `Cross-Origin-Embedder-Policy`) so `SharedArrayBuffer` works. A second run without them tests the fallback path. |
| Harness | A page with one Web Worker running Pyodide, and a message protocol that mirrors the planned `Engine` interface (`loadDataset`, `profile`, `run`, `cancel`). Results are logged as JSON to a download. |
| Native baseline | A local Python environment with the **same library versions** as the Pyodide build (scikit-learn, pandas, XGBoost, pyarrow). Mismatched versions would make the comparison meaningless. |
| Data | Generated by one seeded script so everyone gets identical files. Sizes: 10k, 100k, 500k, 1M rows, each with 20 and 50 columns, mixed types: numeric, low- and high-cardinality categorical, about 5% missing, one datetime column, a binary target and a numeric target. Plus one real public dataset (for example California housing and Adult income) to check realistic behaviour. |
| Hardware | At least two machines. Available: a Mac (MacBook Air, Apple M2, 8 cores, 8 GB RAM, no NVIDIA GPU, which doubles as the lower-end machine) and a Windows machine (specs and whether it has an NVIDIA GPU to be recorded). Record CPU, RAM, GPU, OS for every run. |
| Browsers | Latest Chrome, Firefox and Safari. |

## Measurement rules

- Every timing is the **median of 5 runs**, with the min and max recorded.
- Cold start means an empty cache in a fresh profile. Warm means service-worker cache already filled.
- Timing uses `performance.now()` inside the worker, plus wall-clock from the page for end-to-end.
- Memory: `performance.measureUserAgentSpecificMemory()` where available (needs cross-origin isolation), the browser's own task manager as a cross-check, and the OS process monitor for peak resident size.
- Main-thread responsiveness: record the longest frame gap while a job runs. The UI thread must not stall.
- Record failures as results. A crash is data.

## Experiments

### E1. Load time and download size

- **Method:** measure time to "engine ready" and bytes transferred for each package set, added step by step: Pyodide core, plus numpy and pandas, plus scikit-learn, plus XGBoost, plus pyarrow. Cold with network throttled to about 50 Mbit and unthrottled, and warm.
- **Records:** per-step bytes and seconds, total.
- **Pass (proposed):** warm start to ready under 5 s. Cold start under 30 s at 50 Mbit. Clear plan for loading packages on demand (for example XGBoost only when chosen).
- **Critical:** warm start.

### E2. Data scale: read and profile

- **Method:** for each file, read the CSV in the worker, then compute the full profile defined in [rule-engine.md](../design/rule-engine.md): per-column stats, null %, unique counts, skew, outlier counts, sampled correlations, target balance. Variants: all columns, selected columns only, chunked read, sampled read.
- **Records:** read time, profile time, peak memory, main-thread jank, and the **point of failure**: the first size that runs out of memory, and how it shows up (exception, silent worker death, tab crash).
- **Pass (proposed):** 100k rows × 50 columns reads and profiles in under 20 s with peak memory under 1.5 GB. Larger files either work or fail in a way we can catch before the tab dies, so the app can show the "use a sample or the companion" message.
- **Critical:** the 100k × 50 case, and that failure is detectable.

### E3. Speed against native

- **Method:** same data, same seed, same library versions. Fit and predict for: random forest (100 trees), XGBoost (200 rounds), logistic regression, ridge, KNN predict, K-means, and the scikit-learn MLP. Run in Pyodide, native with one thread, and native with default threads, so the WebAssembly penalty and the no-threads penalty are separate numbers. Check that scores agree closely, which also confirms the two environments behave the same.
- **Records:** fit time, predict time, ratio to native, scores.
- **Pass (proposed):** at 100k × 50, random forest within 5× of single-thread native and under 2 minutes in absolute terms, XGBoost within 3× and under 1 minute. Scores match native within noise. The results also set the preset sizes (Fast, Balanced, Accurate) and the row-count warnings used by rules M05 to M07.
- **Critical:** random forest and XGBoost at 100k.

### E4. Threads

- **Method:** check what `os.cpu_count()` reports in Pyodide, whether `n_jobs > 1` changes anything for random forest, whether XGBoost's thread setting has any effect, and `navigator.hardwareConcurrency`. State plainly whether any library runs in parallel.
- **Records:** observed speed with 1 versus several requested threads.
- **Pass:** none needed. The finding decides whether we tell users the browser engine is single-threaded and push heavy work to the companion.

### E5. Cancellation

- **Method:** with the interrupt buffer, cancel during: a pandas read, a random forest fit, an XGBoost train, and our MLP epoch loop. Repeat without cross-origin isolation to test the terminate-and-restart fallback. Measure the delay from cancel request to stopped.
- **What to expect:** interrupts are only seen when Python code runs, so a long single call into compiled code (an XGBoost round, a large tree build) may not stop until it returns. The test finds out which cases really are interruptible and whether a per-round or per-epoch cancel flag in our callbacks covers the rest.
- **Records:** latency per case, whether it stopped, whether state stayed usable afterwards, and warm restart time for the fallback.
- **Pass (proposed):** every case stops within 2 s using interrupt plus our cancel flag, or within 8 s using terminate-and-restart.
- **Critical:** that some mechanism works for every training path.

### E6. Live events

- **Method:** build the four live-event loops from the table in [engine-choice.md](../architecture/engine-choice.md):
  1. MLP epoch loop with `partial_fit`, reading weights between epochs.
  2. Random forest grown with `warm_start` and rising `n_estimators`.
  3. XGBoost with a training callback.
  4. K-means one iteration at a time.
  Emit real events through `postMessage`, including a downsampled weight matrix as a transferable buffer.
- **Equivalence checks:** (a) warm-started forest versus a one-shot fit with the same seed should give identical predictions, (b) one-step K-means versus a normal fit should reach the same inertia, (c) the manual MLP loop versus a normal MLP fit should land within normal seed-to-seed noise on score.
- **Records:** event overhead as a percentage of training time with events on versus off, maximum sustainable event rate before the main thread stalls, and the results of the three equivalence checks.
- **Pass (proposed):** event overhead under 10% at the default visualisation level. All equivalence checks hold (the MLP within noise). UI stays responsive at 30 messages per second per stream.
- **Critical:** MLP and XGBoost events, and the equivalence checks.

### E7. Caching and storage

- **Method:** check whether `pyarrow` loads in Pyodide. Write the 100k × 50 frame as Arrow and as Parquet, then read back, and record size and speed. Store those blobs in Cache Storage and in IndexedDB, read them back, and record speed. Call `navigator.storage.persist()` and `navigator.storage.estimate()` and note the quota on each browser. Check how each browser evicts: Safari is believed to clear script-written storage after a period without visits, which would affect saved projects (verify and note the exact rule).
- **Records:** availability, sizes, speeds, quotas, eviction behaviour.
- **Pass (proposed):** a cached 100k × 50 node output reloads in under 2 s. If `pyarrow` is missing, name the fallback format.
- **Outcome:** closes the "Arrow or Parquet" open item in [hashing-and-runs.md](../design/hashing-and-runs.md), and the eviction findings feed the "export your project" reminder.

### E8. Browser matrix

- **Method:** run the core flow (E1, E2 at 100k, E3 for one model, E5, E6 for one loop, E7) in Chrome, Firefox and Safari. Also check File System Access handle persistence (Chromium only) and the fallback flow for the others.
- **Records:** a pass / partial / fail table per browser and per experiment.
- **Pass (proposed):** the core flow works in Chrome and Firefox. Safari can have documented gaps if the product degrades gracefully.

### E9. Same code, two runtimes

This tests the main argument for the whole design.

- **Method:** write two or three real node implementations (for example `impute`, `encode`, `model` for logistic regression) as plain pandas/scikit-learn functions in one file. Run that exact file in Pyodide and natively behind a minimal WebSocket server. Feed identical inputs.
- **Records:** whether the file runs unchanged in both, and whether outputs match (identical data frames, equal scores).
- **Pass:** unchanged file, equal outputs.
- **Critical:** yes. If this fails, the single-codebase argument weakens.

### E10. DuckDB-WASM comparison (only if E2 fails)

- **Method:** ingest the same files with DuckDB-WASM, sample and project columns, hand the result to pandas, and measure time and memory against the pandas-only path.
- **Pass:** it handles at least the next size up from E2's failure point, enough to justify a second data stack.

### E11. GPU and platform

- **Method:** detect available devices on each machine: WebGPU adapter in the browser, CUDA (`nvidia-smi`, XGBoost GPU build) on Windows, MPS on the Mac. Benchmark XGBoost and a small neural network on CPU versus GPU natively, and a small ONNX or TF.js model on WebGPU in the browser. Also confirm the Windows run of E1 to E9 behaves like the Mac run.
- **Records:** device list, CPU versus GPU speed, any fallback behaviour, Windows versus Mac differences.
- **Pass:** informational for the CPU engine. For the companion, GPU training must beat CPU on at least one v1 algorithm at 500k rows, otherwise the "Auto picks GPU" policy in [engine-choice.md](../architecture/engine-choice.md) is not worth building yet.

## Decision matrix

| Outcome | Decision |
|---|---|
| All critical items pass | **Go** as designed. Record limits and presets. |
| E3 fails only above some size | **Go**, with the companion offered above that size, and presets and warnings set from the numbers. |
| E2 fails at or below 100k × 50 | Run E10. If DuckDB-WASM rescues it, add it in v1. Otherwise move the default to **companion-first**. |
| E5 shows interrupts work only at callback boundaries | **Go**: boundary cancel plus terminate fallback, as already designed. |
| E1 warm start too slow | Work on loading strategy (on-demand packages, smaller core). Still go unless warm start stays above about 10 s. |
| E6 equivalence checks fail | Replace that algorithm's live loop with a replay, and note it in the event table. |
| E9 fails | Reopen the engine choice: consider a JavaScript engine for the browser and a separate code path. |
| Two or more critical items fail | **No-go** on Pyodide as the default. Re-evaluate options B (JavaScript libraries) and a companion-first product. |

## Risks to the spike itself

| Risk | Mitigation |
|---|---|
| Results depend on one machine | At least two machines, include the lower-end one |
| Library versions differ between Pyodide and native | Pin matching versions, record them |
| Synthetic data hides real problems | Add the real datasets |
| Scope creep into building the product | Throwaway code only, fixed 8-day budget |
| Benchmarks tuned to pass | Thresholds fixed before running (this file) |
